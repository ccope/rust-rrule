# Recurrence corpora

Other libraries' recurrence test suites, stored as data so the same cases can run
against any implementation of this crate. The runners in `tests/` report results.
They do not assert: `cargo test` passes whatever the counts are, and the output
ends with `N cases, P pass, F fail, E errors`.

| File | Source | License | Runner |
| --- | --- | --- | --- |
| `libical_icalrecur_test.txt` | libical `src/test/icalrecur_test.txt` (vendored verbatim, libical's own format) | MPL-2.0 | `tests/libical.rs` |
| `rfc2445_iter_tests.txt` | google-rfc-2445 `RRuleIteratorImplTest.java`, `CompoundIteratorImplTest.java` | Apache-2.0 | `tests/rfc2445.rs` |
| `ical4j_recur_tests.txt` | ical4j `RecurSpec.groovy`, plus selected `RecurTest.java` cases | BSD-3-Clause | `tests/ical4j.rs` |

License texts are in `LICENSES/`. Each data file names its upstream commit in its header.
The last two files are generated by the scripts in `extract/` (Python 3.7+) and should not
be edited by hand:

    python3 extract/rfc2445.py /path/to/google-rfc-2445 > rfc2445_iter_tests.txt
    python3 extract/ical4j.py  /path/to/ical4j          > ical4j_recur_tests.txt

Run them with

    cargo test --features exrule --test rfc2445 -- --nocapture
    cargo test --test ical4j -- --nocapture

The rfc2445 corpus has EXRULE cases. Without `--features exrule` the crate ignores
EXRULE, so the adapter reports those cases as errors instead of letting them fail.

Only `tests/common/adapter.rs` calls the crate. To port the crate to another
date-time library, rewrite that file. `tests/common/corpus.rs` does not change.

## Format

The format is line oriented. A line starting with `#` is a comment: an upstream
note, or a flag on an expectation that looks wrong (`UPSTREAM LOOKS WRONG`,
`UPSTREAM ARTEFACT`). Blank lines are ignored. Every other line is `KEY:value`. A
case starts at `CASE:` and runs until the next `CASE:`.

| Key | Meaning |
| --- | --- |
| `CASE:<file>#<test>[ <detail>]` | Starts a case and names the upstream test it came from. |
| `TZ:<IANA zone>` | The zone that floating values are interpreted in. Defaults to `UTC`. |
| `DTSTART:<value>` | The series start. See *Values*. |
| `DTSTART-INSTANCE:always\|if-matches` | `always`: DTSTART is an instance even if the rules do not generate it (RFC 5545 §3.8.5.3, and google-rfc-2445's compound iterator). `if-matches`: it is an instance only if the rules generate it. |
| `RRULE:` `EXRULE:` `RDATE[;params]:` `EXDATE[;params]:` | Content lines of the recurrence set, verbatim from upstream except that folded lines are unfolded and blank lines dropped. There can be any number of them. |
| `ADVANCE-TO:<value>` | Keep only instances `>= value`. |
| `AFTER:<value>` | Keep only instances `> value`. |
| `WINDOW:<start>/<end>` | Keep only instances with `start <= i <= end`. Both ends are inclusive. |
| `LIMIT:<n>` | Compare only the first `n` instances that remain after the bounds. |
| `MORE:yes\|no\|any` | Whether an instance exists past `LIMIT` (upstream's trailing `,...`). Defaults to `no` when `LIMIT` is set. `any` means upstream did not check. |
| `INSTANCES:<v>,<v>,...` | The expected instances, in order. An empty value means no instances. |
| `INSTANCES-AS:utc\|utc-z\|local\|local-offset` | How a DATE-TIME instance is printed. `utc` prints the UTC wall clock as `YYYYMMDDTHHMMSS`. `utc-z` adds a trailing `Z`. `local` prints the wall clock in `TZ`. `local-offset` adds the UTC offset, as in `20250309T030000-0700`. DATE instances are always `YYYYMMDD`. |
| `COUNT:<n>` | Asserts the number of instances. Used alone when upstream asserts only a count. |
| `NTH:<i>=<value>` | Asserts only the instance at 0-based index `i`. |
| `SAME-AS:<rule>` | The expected instances are those of this RRULE value, evaluated with the case's other parameters in place of the case's RRULE. |

### Values

- `YYYYMMDD` is a DATE. DATEs have no zone. A runner evaluates them as midnight UTC
  whatever `TZ` says. In a bound or an `UNTIL`, a DATE means 00:00 on that day.
- `YYYYMMDDTHHMMSS` is a floating DATE-TIME, interpreted in `TZ`.
- `YYYYMMDDTHHMMSSZ` is UTC.

The same rules apply inside RRULE/EXRULE `UNTIL`, and to RDATE/EXDATE values that carry
no `TZID` parameter.

### Checking a case

A runner expands the set, then keeps only the instances inside `ADVANCE-TO`, `AFTER`
or `WINDOW`. It then asserts every key the case sets: `INSTANCES` (the first `LIMIT`
instances when `LIMIT` is set), `MORE`, `COUNT`, `NTH` and `SAME-AS`. If the
implementation cannot express a case (it rejects the rule, or lacks a feature), the
case is an error, not a failure.

## Source semantics

### google-rfc-2445

- `runRecurrenceIteratorTest(rrule, dtStart, limit, golden[, advanceTo][, tz])`
  iterates at most `limit` instances. A trailing `,...` in `golden` means another
  instance exists (`MORE:yes`). `tz` defaults to UTC. Upstream prints instances
  converted to UTC and without a `Z` (`INSTANCES-AS:utc`).
- When no `advanceTo` is given, the helper runs the case a second time with
  `advanceTo = dtStart`. The extractor writes that second run out as its own case,
  suffixed `advanceTo=dtStart`.
- `advanceTo()` takes a UTC value, so a DATE-TIME `ADVANCE-TO` is written with a `Z`.
  In the PST cases this is not the same instant as DTSTART.
- The RRule iterator yields DTSTART only if the rule generates it (`if-matches`). The
  compound iterator (`createRecurrenceIterator(rdata, …)`) always includes DTSTART
  (`always`).
- An `UNTIL` whose type differs from DTSTART's is coerced to DTSTART's type: a DATE
  becomes 00:00Z that day, and a DATE-TIME is truncated to its date. The value rules
  above give the same instances for every case in this corpus. The only DATE `UNTIL`
  with a DATE-TIME DTSTART is in a `TZ:UTC` case, where 00:00Z and 00:00 local are
  the same instant.
- `testMonkeyHourly` passes the text `EXRULE:…` to `new RRule()`. That iterator
  treats every rule as a generator, so the case is stored as `RRULE:`.
- Not extracted. `testFrequencyLimits` asserts nothing.
  `testIdenticalInclusionsAndExclusionsNoDtstartPrivilege` builds a
  `CompoundIteratorImpl` directly with no DTSTART, which the format cannot express.
- Transcribed by hand in the extractor (`HAND_RRULE`, `even_weeks`, and
  `testMultipleChecksDontChange`). These tests assert on a hand-written loop, or
  compute their golden in Java.

### ical4j

- `Recur.getDates(seed, periodStart, periodEnd)`: DTSTART is the seed, and `WINDOW`
  is `[periodStart, periodEnd]`, inclusive at both ends (`RecurDateSpliterator`: a
  candidate is kept when it is neither before `periodStart` nor after `periodEnd`,
  whatever the code comment says). The seed is an instance only if the rule
  generates it. COUNT counts from the seed, including instances before the window.
  `getDates(start, end)` uses `start` as the seed.
- `getNextDate(seed, start)` returns the first instance strictly after `start`
  (`AFTER`, `LIMIT:1`). If upstream expects `null`, the case expects no instances.
- `TemporalComparator` compares a DATE `UNTIL` as 00:00 that day.
- The Spock specs read floating values (`LocalDate`, `LocalDateTime`), with the
  `date.floating` property set. They run as `TZ:UTC`. Specs that parse with a zone
  keep that zone.
- The `RecurTest.java` cases are hand-picked, and the whole class is `@Disabled`
  upstream, so ical4j's build does not check their expectations. The following
  were not taken:
  - Anything seeded from `ZonedDateTime.now()`. Those expectations are not fixed values.
  - `testGetDatesCalendarField`, `testGetDatesOrdering`, `testGetDatesNotEmpty` and
    `testGetDatesTimeZone`. They assert a property of every date, not specific values.
  - The `everyThirdMonWedThu` getNextDate case. Its expectation comes from ical4j's
    own `getDates`.
  - The parse, string-form and invalid-rule tests.
- `RecurSpec` features about parsing, string forms, builders and validation are not
  extracted. From `duplicate candidates …` only the `getDates` comparison is taken,
  not the `getNextDate` assertions.

## google/

Google Calendar's own expansion, the reference the others are checked against.
`synthetic-spec.json` lists recurring series that each isolate one question
(its `note` says which). schedule-me's
`devtool recurrence-fixtures --spec synthetic-spec.json --out synthetic.json`
writes them to a scratch calendar in a test account, records the master Google
echoes back and every instance (cancelled ones included) over `time_min` to
`time_max`, keeping only scheduling fields, and deletes the calendar again.
`tests/google.rs` rebuilds each series from the spec's DTSTART and Google's
recurrence lines and compares against each instance's `originalStartTime`.

Captures derived from a real account's calendars go in `google/private/`,
which git ignores; the runner includes them when present.
